## 1. 概述

本规范定义 **seeinps ↔ seeinpm** 之间的控制协议与数据转发协议。所有通信承载于**一条 TLS 长连接**（默认端口 99），控制信令与代理数据在连接内通过 **mux 多路复用**（smux/yamux）分通道传输，与 frp 的 tcpmux 模型一致。

### 1.1 通信原则

| 原则 | 说明 |
|---|---|
| 主动外连 | 仅 seeinps 主动连接 seeinpm；seeinps 无需公网 IP、无需开放入站端口 |
| 单一连接 | seeinps 与 seeinpm 之间建立**一条** TLS 连接，内部 mux 分多个逻辑流 |
| 加密传输 | 默认 TLS 1.2+；自签证书场景通过部署工具分发指纹（pinning）；可选 mTLS |
| 版本协商 | 握手阶段协商协议版本，不兼容即拒绝并携带提示 |
| 信令 JSON | 控制信令使用 JSON（UTF-8）编码，长度前缀分包；数据载荷为原始字节流 |

### 1.2 连接参数

| 参数 | 默认值 | 说明 |
|---|---|---|
| 服务器地址 | see.timesee.cn | seeinpm 域名（见 seeinps 配置文件） |
| 服务器端口 | 99 | 见端口矩阵（01-需求文档 §3.2） |
| TLS | 强制启用 | 证书校验：指纹固定（首选）或 CA 校验 |
| 心跳间隔 | 10s | 应用层心跳 |
| 心跳超时 | 3 次未响应判定离线 | seeinpm 侧回收该用户端口并标记离线 |

## 2. 报文格式

### 2.1 帧格式（控制信令）

控制信令采用「4 字节大端长度 + JSON 载荷」：

```
┌──────────────┬─────────────────────────────┐
│ length(4B)   │ payload (JSON, UTF-8)       │
└──────────────┴─────────────────────────────┘
```

### 2.2 通用消息结构

所有控制消息遵循统一外壳：

```json
{
  "type": "REGISTER",          // 消息类型（见 §9 错误码表与消息清单）
  "id": "msg-6f2c...",         // 消息 ID（请求-响应配对，UUID）
  "version": "1.0",            // 协议版本（仅在 HELLO/REGISTER 携带）
  "ts": 1785912345,            // 发送方 Unix 时间戳
  "data": { ... }              // 类型相关载荷
}
```

响应统一携带 `code`（0 成功，非 0 见错误码表）：

```json
{ "type": "REGISTER_RESP", "id": "msg-6f2c...", "code": 0, "data": { ... } }
```

### 2.3 数据通道帧（代理数据流）

数据不封装 JSON，直接在 mux 逻辑流内透传原始字节；逻辑流头部标记流属性（streamType + proxyId）：

```
┌──────────┬──────────────┬──────────┬───────────────────────┐
│ stype(1B)│ proxyIdLen(1B)│ proxyId │ 原始数据载荷（变长）     │
└──────────┴──────────────┴──────────┴───────────────────────┘
stype: 0x01=TCP映射 0x02=UDP会话 0x03=HTTP代理流 0x04=运维代理流 0x05=升级包流（无 proxyId，头部为 4B 大端长度 + JSON 元信息 {releaseId,version,sha256,size} + 二进制内容；见 §升级流程）
proxyIdLen: proxyId 字节数（1-128），读方按长度精确读取，防止与载荷粘连
```

## 3. 连接建立与版本协商

### 3.1 握手时序

```
seeinps                                   seeinpm
   │  TCP+TLS 连接 (see.timesee.cn:99)        │
   │──────────────────────────────────────────►│
   │  HELLO {version:"1.0", arch, os, build}   │
   │──────────────────────────────────────────►│
   │  HELLO_RESP {code:0, version:"1.0",       │
   │              serverVersion, caps:[...]}   │
   │◄──────────────────────────────────────────│
   │  (版本不兼容: code:1004 VERSION_MISMATCH)  │
```

### 3.2 版本策略

| 规则 | 说明 |
|---|---|
| 兼容判定 | 主版本必须一致；次版本要求 `server.major == client.major && server.minor >= client.minor` 且双方均支持的 minor 范围内 |
| 拒绝行为 | 版本不兼容时 seeinpm 返回 `1004 VERSION_MISMATCH`，载荷含「最低支持版本」与升级提示；seeinps 记录日志并停止重连（除非用户手动覆盖） |
| 能力协商 | `caps` 数组声明支持的能力（mux、tls、ops_proxy、udp、acl_v1 等），后续消息不得使用未协商能力 |

## 4. 注册流程（授权码 + 用户名）【运行细节②，与需求文档 §5.2 严格一致】

### 4.1 时序

```
seeinps 部署工具 / seeinps             seeinpm
   │  HELLO → HELLO_RESP 成功                │
   │  REGISTER {username, authCodeHash}      │
   │────────────────────────────────────────►│
   │  → 校验：username 存在且 authCodeHash   │
   │    与存储匹配（不校验任何密码）           │
   │  → 单实例检查：该授权码是否已在线        │
   │  REGISTER_RESP {code:0, session:{...}}  │
   │◄────────────────────────────────────────│
   │  或 code:1001 AUTH_FAILED               │
   │  或 code:1002 AUTH_CODE_IN_USE          │
   │  或 code:1003 SESSION_REVOKED (用户禁用)│
```

### 4.2 注册载荷

```json
{
  "type": "REGISTER",
  "username": "ops01",
  "authCodeHash": "sha256:ab12...",     // 授权码的 SHA-256（盐值由 HELLO_RESP 下发）
  "os": "linux", "arch": "amd64",
  "hostname": "nas-host",
  "natType": "fullcone"                 // 可选，信息性
}
```

> **安全细节**：授权码**永不**以明文在网络传输。HELLO_RESP 下发一次性盐值，seeinps 用 `SHA-256(salt + authCode)` 后传输；seeinpm 侧用同样算法与存储哈希比对。存储为 `bcrypt(sha256(salt+code))`（见 04-数据存储规范 §3.1）。

### 4.3 注册响应（成功）

```json
{
  "type": "REGISTER_RESP", "code": 0,
  "data": {
    "sessionId": "sess-9f3a...",
    "sessionKey": "base64...",          // 会话密钥（数据通道 HMAC 用），每会话轮换
    "userConfig": {                     // seeinpm 侧该用户配置快照
      "portPoolRestricted": null,       // 或 ["20000-25000"]
      "maxProxies": 100,
      "maxBandwidth": 0                 // 0=不限
    },
    "assignedProxies": [ ... ]          // 此前已分配的端口/代理列表（重启恢复用）
  }
}
```

### 4.4 单实例冲突（授权码已被占用）

- seeinpm 检测到该授权码已有**真正活跃**的在线会话（内存中存在该用户的连接、心跳新鲜（90s 内有上报）、且 mux 会话未关闭）→ 返回 `1002 AUTH_CODE_IN_USE`，载荷含 `onlineSince`（原实例在线时间）、`connectedFrom`（脱敏 IP）；
- **部署工具**收到 1002 时弹窗提醒「该授权码已被使用」，默认拒绝继续部署（用户可查看详情）；
- 若为新连接请求且原实例心跳已超时（离线判定完成），则接受注册并踢掉原会话；
- **残留会话自动替换**：数据库 `online_session` 为残留值时（如 seeinpm 重启后无人清理、或旧连接已死但心跳协程尚未退出），seeinpm 直接清除残留并接受新注册，不再返回 1002——否则 seeinps 会因旧值永远无法重连；
- 被替换的旧连接退出时按 sessionID 条件清理（`ClearUserOnlineStatusIfSession`），不会误删新会话的在线状态（否则清理例程会误释放新会话的端口）。

### 4.4.1 会话吊销（用户被禁用/授权码被重置）【已实现】

- **注册时拒绝**：用户处于禁用状态（`users.status = 0`）时，即使授权码正确，REGISTER 也返回 `1003 SESSION_REVOKED`，载荷 `{reason: "user_disabled"}`；
- **在线时吊销**：seeinpm 管理端禁用用户（`disconnectNow=true`）或重置授权码时，先在控制流推送 `SESSION_REVOKE`（载荷 `{reason: "user_disabled" | "auth_code_reset"}`），再关闭该用户的 yamux 会话，并停止其全部公网监听、释放端口；
- **seeinps 侧行为按 reason 区分**：
  - `auth_code_reset` → **停止重连，进程保持运行**：B端 web 继续可用并提示「授权码已被重置」，管理员在 seeinps 管理页输入新授权码（`POST /api/v1/auth/rebind`，见 API §3.1）后自动重连；代理数据完整保留，重连成功后端口复用恢复全部代理，无需重新部署；
  - `user_disabled`（含断开后重连注册收到 1003）→ 断开连接并进入**低速重试**（固定 10s），管理员重新启用后最多 10s 内自动恢复，无需重启 seeinps；
- 普通断线仍走指数退避重试（1s→60s 封顶），与吊销行为无关。

### 4.5 注册后

- seeinpm 将该 seeinps 标记在线，恢复其端口分配（若 seeinpm 曾重启），下发差量配置；
- seeinps 启动本地代理引擎，逐条确认代理就绪（`PROXY_READY`），B端显示「在线」。

## 5. 鉴权与会话管理

| 消息 | 方向 | 说明 |
|---|---|---|
| `SESSION_RENEW` | 双向 | 会话密钥轮换（默认每 24h 或传输量超 1GB 触发），轮换时旧密钥保留 2 个滑动窗口防乱序 |
| `SESSION_REVOKE` | pm→ps | seeinpm 吊销会话（用户被禁用/授权码被重置时），载荷 `{reason}`；seeinps 收到后断开：授权码重置则停止重连（进程保持运行，B端输入新授权码重绑后自动恢复），用户禁用则低速重试待启用【已实现，见 §4.4.1】 |
| `PROXY_REVOKE` | pm→ps | seeinpm 禁用单个代理（管理端「代理管理」操作），载荷 `{proxyId, reason: "proxy_disabled"}`；seeinps 收到后清除该代理的转发端口标记（ForwardPort=0），由 30s 周期的 resync 重试 `ALLOC_PORT`：禁用期间被拒绝（1006），管理员启用后自动恢复；同用户其他代理不受影响【已实现】 |
| `PING` / `PONG` | 双向 | 心跳，10s 间隔；`PONG` 携带双方负载指标（可选） |

## 6. 心跳与状态上报

### 6.1 心跳

```json
{ "type": "PING", "id": "m1", "ts": 1785912345 }
{ "type": "PONG", "id": "m1", "ts": 1785912355, "data": {"cpu": 12.3, "mem": 45.1, "conns": 32} }
```

- seeinpm 连续 3 个心跳周期未收到 PING → 判定该 seeinps 离线 → 回收其端口池端口、标记代理离线、记录断开时间（历史记录）；
- seeinps 未收到 PONG → 判定控制通道异常 → 走重连（指数退避 1s/2s/4s…上限 60s + 抖动 30%）。

### 6.2 状态上报（周期 + 事件双模式）

| 模式 | 触发 | 内容 |
|---|---|---|
| 周期上报 | 默认 15s | 各代理连接数、瞬时速率、队列深度 |
| 事件上报 | 连接建立/断开/认证失败 | 单条连接记录（见下） |

```json
{
  "type": "REPORT",
  "data": {
    "period": {"since": 1785912300, "until": 1785912345},
    "items": [
      {"proxyId": "px-01", "type": "tcp", "activeConns": 5,
       "rxBytes": 1048576, "txBytes": 524288}
    ]
  }
}
```

### 6.3 连接事件

```json
{
  "type": "CONN_EVENT",
  "data": {
    "proxyId": "px-01", "connId": "c-7f1a",
    "event": "open" | "close" | "auth_fail",
    "clientIp": "203.0.113.9",           // seeinpc 侧公网来源 IP
    "target": "10.0.0.5:3306",
    "rxBytes": 0, "txBytes": 0,
    "reason": "auth_failed"              // close 时的原因
  }
}
```

seeinpm 将事件写入访问日志与 `connections` 表（04-数据存储规范 §3.1），供 B端历史/统计查询。

## 7. 配置下发

| 消息 | 方向 | 说明 |
|---|---|---|
| `CONFIG_PUSH` | pm→ps | seeinpm 主动推送配置变更（管理员在 seeinpm B端调整该用户限制/端口池后），增量格式 |
| `CONFIG_PULL` / `CONFIG_PULL_RESP` | ps→pm / pm→ps | seeinps 启动/重连后拉取全量配置 |

```json
{ "type": "CONFIG_PUSH", "data": { "revision": 42, "changes": [
    {"op": "upsert", "path": "userConfig.maxProxies", "value": 50}
] } }
```

**冲突规则**：以 seeinpm 侧配置为准；seeinps 本地修改代理配置需先向 seeinpm 申请（端口分配类），纯本地项（如代理密码）不同步到 seeinpm。

## 8. 数据通道与端口分配

### 8.1 端口分配（ALLOC_PORT）

由 seeinps 发起（添加 TCP/UDP 映射、运维代理时），**运维ID 的产生即本流程**（需求文档 §4.2 运行细节④）：

```json
// 请求（seeinps → seeinpm）
{
  "type": "ALLOC_PORT",
  "data": {
    "proxyType": "tcp" | "udp" | "ops_http" | "ops_socks",
    "preferredPort": null,        // 可选：端口池内指定端口；null=随机
    "proxyName": "mysql-master"
  }
}

// 响应（seeinpm → seeinps）
{
  "type": "ALLOC_PORT_RESP", "code": 0,
  "data": {
    "proxyId": "px-9b2f",         // 全局唯一代理 ID
    "publicPort": 23456,          // 对外端口（= 运维ID，仅 ops 类型对外展示）
    "portPoolId": "pool-01"
  }
}
```

失败码：`3001 PORT_CONFLICT`（端口占用）、`3002 PORT_POOL_EXHAUSTED`（池耗尽）、`3003 OUT_OF_RANGE`（超出该用户限制区间，服务端强校验）。

### 8.2 TCP 映射数据流

```
外网客户端 ──► seeinpm:对外端口
                 │ mux 新逻辑流 (stype=0x01, proxyId)
                 ▼
             seeinps ──► 内网服务 (127.0.0.1:3306)
```

- 每一条外部连接在 mux 上开辟一个逻辑流；数据双向透传；
- 关闭：任一端 EOF → 关闭另一端 → 发送流关闭帧。

### 8.3 UDP 映射数据流

- 对外监听使用 UDP socket；以「源地址 + 目标地址」五元组维护**会话表**；
- 每个会话映射一个 mux 逻辑流（stype=0x02）；会话空闲超时（默认 120s，可配）回收；
- seeinps 侧同样维护本地 UDP 会话，超时同步回收。

### 8.4 HTTP / SOCKS5 运维代理数据流（认证在 seeinps 侧）

```
seeinpc ──► see.timesee.cn:运维ID (seeinpm 监听)
             │ mux 新逻辑流 (stype=0x04, proxyId=ops代理)
             ▼
        seeinps 认证器：校验 Proxy-Authorization: Basic / SOCKS5 RFC1929
             │ 通过：转发至目标（ACL 校验后）
             ▼
        内网目标
```

- **认证发生在 seeinps 侧**（密码仅本地）；认证失败 seeinpm 回 `407 Proxy Authentication Required`（HTTP）/ SOCKS5 认证失败码（0xFF）；
- ACL（目标网段白名单/黑名单）在 seeinps 认证器上执行，命中黑名单返回 `403` 并记访问日志；
- seeinpm 对运维代理端口做**准入限流**（未认证连接数上限、单来源 IP 速率），防止端口扫描爆破。

### 8.5 mux 多路复用

- 采用 smux/yamux 实现；控制消息与数据流共享一条 TLS 连接；
- 流 ID 空间：控制信令用独立保留流（stream 0），数据流从 1 递增；
- 拥塞控制：数据流写缓冲上限（默认 4MB/流），超限背压到转发方；
- 连接级 keepalive：复用 TLS 层 + 应用层心跳双保险。

## 9. 错误码表（控制通道）

| 码 | 名称 | 说明 |
|---|---|---|
| 0 | OK | 成功 |
| 1000 | INTERNAL | 内部错误（含详情但不泄露敏感信息） |
| 1001 | AUTH_FAILED | 用户名或授权码不匹配 |
| 1002 | AUTH_CODE_IN_USE | 授权码已被其他实例占用（单实例冲突，部署工具弹窗提醒） |
| 1003 | SESSION_REVOKED | 会话被吊销（用户被禁用/授权码被重置） |
| 1004 | VERSION_MISMATCH | 协议版本不兼容（含最低版本与升级提示） |
| 1005 | RATE_LIMITED | 请求过于频繁（防爆破） |
| 1006 | PROXY_DISABLED | 代理被管理员禁用（ALLOC_PORT 拒绝）；seeinps 低速重试，管理端启用后自动恢复【已实现】 |
| 2000 | BAD_REQUEST | 报文格式错误/字段缺失 |
| 2001 | UNSUPPORTED_TYPE | 未知消息类型 |
| 3001 | PORT_CONFLICT | 端口冲突 |
| 3002 | PORT_POOL_EXHAUSTED | 端口池耗尽 |
| 3003 | OUT_OF_RANGE | 端口超出该用户限制区间（服务端强校验） |
| 3004 | PROXY_LIMIT | 超过该用户最大代理数 |
| 3005 | BANDWIDTH_EXCEEDED | 超出带宽配额（限流触发） |

## 10. 完整时序图（文字版）

### 10.1 部署 + 首次注册（含授权码校验）

```
部署工具(Windows)          see.timesee.cn:90(seeinpm)          seeinps(目标机)
     │ 校验授权码+用户名         │                                     │
     │──(HTTPS API) /api/v1/auth/verify-code──►│                     │
     │◄── code:0 / 1001 / 1002 ──│                                     │
     │  (1002 → 弹窗提醒，默认拒绝)│                                     │
     │───────── 上传二进制/生成配置/systemd ──────────────────────────►│
     │◄────────────────────────── 部署完成，启动 seeinps ─────────────│
     │                                     │◄── TLS + HELLO ──────────│
     │                                     │◄── REGISTER(user,authHash)│
     │                                     │── REGISTER_RESP(code:0) ─►│
     │◄──────────── 状态: 在线（B端可见）──────────────────────────────│
```

### 10.2 运维代理连接（seeinpc 使用）

```
seeinpc                      seeinpm(:运维ID)                seeinps(认证器)     内网目标
   │  CONNECT + Proxy-Authorization │                             │              │
   │────────────────────────────────►│  mux 新流(0x04)            │              │
   │                                 │────────────────────────────►│  ACL 校验    │
   │                                 │                              │─────连接────►│
   │◄────────────────────────────────│──────────────────────────────│              │
   │  407(认证失败) / 数据双向转发     │                              │              │
```

### 10.3 断线重连

```
seeinps                               seeinpm
   │ PING ──► (无 PONG × 3)             │
   │← 判定离线：回收端口、记断开时间     │
   │ 指数退避 1s→2s→4s…→60s             │
   │ 重新 TLS + HELLO + REGISTER        │
   │← REGISTER_RESP(code:0) + 全量配置  │
   │ 恢复全部代理（PROXY_READY 逐条确认）│
```

## 11. 实现约束（对两端开发的要求）

| 项 | 要求 |
|---|---|
| 幂等 | 所有请求支持重发，通过消息 ID 去重；REGISTER 重复提交返回当前会话状态而非新建 |
| 有序性 | 同一代理的流内数据严格有序（TCP 语义）；跨流不保证 |
| 背压 | 数据流缓冲上限 + 背压，禁止无界队列（防内存膨胀） |
| 时间 | 所有时间戳 UTC Unix；展示层转本地时区（B端） |
| 日志 | 控制通道消息摘要记 DEBUG 日志（含 msg id），敏感载荷脱敏 |
| 兼容 | 新增消息类型必须向后兼容：未知类型返回 `2001 UNSUPPORTED_TYPE` 且不中断连接 |

## 升级流程（2026-08-29 实现，v1 仅 seeinps）

版本管理升级采用「控制通道通知 + 0x05 数据流直传」：

1. A 端管理员触发升级：发送 `UPGRADE_PUSH`（载荷 `{releaseId, version, goos, goarch, sha256, size}`），B 端预检
   （平台与自身一致、包元信息、磁盘空间）后回 `UPGRADE_PUSH_RESP`（code=0 accepted / 非 0 拒绝，data.stage=accepted|failed，data.error）。
2. A 端打开 stype=0x05 的 mux 数据流，写入 `4B 大端长度 + JSON 元信息 + 二进制内容`，写完关闭流（FIN）。
3. B 端边收边算 SHA256，校验大小与摘要通过后：rename 运行中二进制为 `.old` → 新文件顶替原路径 →
   `syscall.Exec` 原地重启（无需 systemd）；校验失败删除临时文件。
4. B 端经控制流发送 `UPGRADE_REPORT`（载荷 `{version, stage: downloaded|failed, error}`）异步上报结果；
   最终成功以重启重连后 HELLO 上报的新版本号为准，A 端 `/api/v1/clients` 可观察版本变化。

## B 端自主升级（2026-08-30 实现）

B 端（seeinps）可主动向 A 端查询/拉取升级包（无需 A 端管理员触发）：

1. `VERSION_LIST_REQ`（B→A，空载荷）→ `VERSION_LIST_RESP`（按 B 端平台过滤的 `{items:[{id,version,note,fileSize,createdAt}]}`）
2. `VERSION_PULL_REQ`（B→A，载荷 `{version}`）→ `VERSION_PULL_RESP`（载荷同 UPGRADE_PUSH：`{releaseId,version,goos,goarch,sha256,size}`）
3. A 端应答后经 0x05 数据流直传二进制，B 端接收校验应用流程与推送升级完全一致
